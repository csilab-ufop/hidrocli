# AGENTS.md

HidroCLI is a Python 3.12 CLI and worker pool that downloads ANA Hidro
WebServices data into two local SQLite databases via SQLAlchemy.

## Setup and commands

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -e ".[dev]"

.venv/bin/python -m pytest -q                    # 87 tests, no network
.venv/bin/python -m pytest tests/test_transform.py::test_convert_json_items -q
.venv/bin/python -m hidrocli --help
```

- The application has no console-script entry point; run `python -m hidrocli`,
  not `hidrocli`. `hidrocli/__init__.py` reads the version from distribution
  metadata, so the package must be installed or the import fails.
- Run from the repository root. `tests/test_transform.py` reads fixtures through
  `./tests/json/...`.
- `hidro-docs` regenerates the wiki: pydoc-markdown, wiki post-processing,
  then the curated models page. The same workflow is available directly from
  `scripts/generate_hidro_models_doc.py`.
- `Makefile` is gitignored/local and partly stale. Trust `pyproject.toml` and
  the direct commands above; for example `make run` relies on an installed
  package and `make run-dirty` passes flags that no longer exist.
- The only configured lint is `ruff check --select F401` (`make check`); there
  is no typecheck step.

## Runtime behavior

- The **Hidro DB** (`db/hidro.db`) holds downloaded reference and series data.
  The **Client DB** (`db/client.db`) holds ANA credentials/token and the
  persistent job queue (`BaseJobs`, `StationJobs`, `SeriesJobs`).
- `orchestrator.run()` always processes all `JobConfig.Base` reference jobs
  first, then series jobs. `--run-for` and `--skip-for` filter only series
  jobs; `--skip-series-jobs` skips all series work.
- `--stations` only filters which already-created pending series jobs are
  triggered in that run. Job rows for all stations are still created, and a
  later run without `--stations` can pick them up.
- `setup_database()` creates missing tables and prompts for the ANA API
  username/password when the client DB has no credentials. Do not run a real
  sync casually: it hits the live API and can write large datasets.
- `config.setup_arguments()` must run before `orchestrator.run()`; it sets the
  module globals (`MAX_WORKERS`, `BATCH_SIZE`, filters) used by the
  worker/writer threads.
- `db/*` and `json/*` are gitignored data caches. Do not delete them or run
  destructive targets such as `make clean-db`/`make clean-all`.
- `setup_logger()` installs custom `TRACE` (15) and `VERBOSE` (5) levels.
  `logger.verbose/trace` do not exist until it has been called.

## Architecture

- Entrypoint: `hidrocli/__main__.py` -> `config.setup_arguments()`,
  `setup_logger()`, `setup_database()` -> `etl.orchestrator.run()`.
- `hidrocli/etl/specs.py` is the single source of truth: one `JobSpec` per job
  (endpoint, ORM model, job model, verify keys, dedupe/date keys, period
  columns, load strategy). `JobConfig` string values are overloaded: they are
  SQLite table names, job names, API endpoint keys, and CLI choices.
  `JobConfig.Status` values are `Enum(auto)` integers: 1 pending, 2 failed,
  3 invalid, 4 corrupted, 5 completed; some SQL hardcodes these numbers.
- The ETL pipeline is split by concern:
  `etl/extract.py` (HTTP + token), `etl/transform.py` (convert/validate/filter
  as pure functions over dicts), `etl/load.py` (upsert + job status),
  `etl/orchestrator.py` (composes E/T/L, runs the thread pool/queue).
- ANA JSON is mapped to ORM rows by each Hidro model's `from_json` classmethod.
  `etl/load.handle_batch_update()` upserts using the keys from the job's spec.
- `orchestrator.trigger_job()` runs a `ThreadPoolExecutor` of request workers
  with a single `db_writer` thread consuming `write_queue`; data is inserted in
  `--batch-size` batches.

## Adding or changing a series job

A series job now touches two places:

- `hidrocli/etl/specs.py`: one `JobSpec` entry in `SPECS` (endpoint, model,
  verify/dedupe/date keys, period columns, load strategy).
- `hidrocli/models/hidro.py`: the table model + its `from_json` classmethod.

`config.py` derives the `--skip-for`/`--run-for` choices from `SPECS`, and
`database/client.py`/`database/hidro.py` read their lookups from it.

## Testing and conventions

- Tests use `unittest.mock.patch` and temporary SQLite databases; they never
  need credentials or network access. Patch names where they are used
  (`hidrocli.etl.orchestrator.*`, `hidrocli.database.client.CLIENT_DB`,
  `hidrocli.database.hidro.HIDRO_DB`), not the original module.
- `HIDRO_DB`/`CLIENT_DB` are `None` until `init_db()` or a test patches them.
- `tests/test_models_{hidro,client}.py` are placeholders.
- Commit messages feed `python-semantic-release` configured in
  `pyproject.toml` (`main` branch; `feat` = minor, `fix` = patch). Use
  Conventional Commits.
- `wiki/` is a git submodule generated by `make doc`/`hidro-docs`; edit source
  docstrings and `hidrocli_docs/docs.py` rather than generated wiki pages.
